From DevOps engineer to AI infrastructure engineer

A 26-week plan for DevOps, cloud and platform engineers who want to move into AI infrastructure. You keep the skills that already pay, add the layer companies are short of, which is running AI models in production, and build public proof that you can do it.

The core idea

Most DevOps engineers learning AI collect course certificates. You will collect numbers: cost per million tokens, time to first token, GPU utilization, and money saved for your company. Hiring managers remember numbers, and they're difficult to fake.

02 · START HERE

The AI job market for DevOps engineers

AI did not replace DevOps. It added an expensive new kind of workload. A GPU node costs 10–50× more per hour than a typical web node, model files are gigabytes in size, and traffic is measured in tokens rather than requests. Companies need people who can run these workloads reliably and cheaply, and very few people have both the infrastructure skills and the AI knowledge.

Primary · AI infrastructure

Run the machines that run models

GPU clusters, model serving with vLLM and KServe, autoscaling, and GPU cost control. It builds on your Kubernetes, Terraform and AWS skills, and it's the hardest of the three to automate away.

Second skill · LLMOps

Run the apps built on models

Gateways, RAG pipelines, evaluations, tracing, guardrails and token budgets. Every company that calls LLM APIs needs this now.

Awareness · MLOps

Pipelines for training models

MLflow, Kubeflow and feature stores. Learn the vocabulary, but don't specialize. Classic MLOps tooling is consolidating into managed platforms.

03 · START HERE

The AI infrastructure stack

This is the map for the whole plan. Today you know the orchestration layer from the application side. By week 26 you'll have run every layer yourself and measured it.

GPU memory, the one formula to learn first

Most AI infrastructure decisions start with a single question: does the model fit in GPU memory? Learn this before you touch a GPU.

VRAM ≈ parameters × bytes per parameter × 1.2  (+ KV cache for long contexts and many users)
Model sizeFP16 (2 B)INT8 (1 B)INT4 / AWQ (0.5 B)Smallest practical AWS GPU
1.5B~4 GB~2 GB~1 GBAny GPU, even g4dn (T4 16 GB)
7–8B~18 GB~9 GB~5 GBg5 (A10G 24 GB) or g6 (L4 24 GB)
14B~34 GB~17 GB~9 GBg6e (L40S 48 GB), or g5 with AWQ
70B~168 GB~84 GB~42 GBp4d / p5 (multiple A100 / H100 GPUs)

Weights plus about 20% overhead. Leave additional headroom for the KV cache, which grows with context length × concurrent requests.

import subprocess

out = subprocess.run(
    ["kubectl", "get", "pods", "-A", "-o", "json"],
    capture_output=True, text=True, check=True,
).stdout

for pod in json.loads(out)["items"]:
    for cs in pod["status"].get("containerStatuses", []):
        if cs["restartCount"] > 3:
            ns, name = pod["metadata"]["namespace"], pod["metadata"]["name"]

Pythonapp.py · week 3 log summarizer
from fastapi import FastAPI
from openai import OpenAI
from pydantic import BaseModel

app = FastAPI()
client = OpenAI()  # in Phase 3, point base_url at your own LLM gateway


class Logs(BaseModel):
    text: str


@app.post("/summarize")
def summarize(logs: Logs):
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": "You are an SRE. List the errors and the likely root cause in 5 bullets."},
            {"role": "user", "content": logs.text[-12000:]},  # keep the newest lines; tokens cost money
        ],
    )
    return {"summary": resp.choices[0].message.content, "tokens": resp.usage.total_tokens}
Phase 1 is done when
  • You can write a 50-line Python script without copying from a tutorial.
  • You can explain, without notes, why a 7B model in FP16 does not fit on a 16 GB GPU.
  • Your log summarizer runs in a kind cluster and reports token usage on every call.

One-page proposal template

Problem

"We call LLM APIs from N services with M separate keys. We can't see spend per team, keys are hard to rotate, and a provider outage takes features down."

Proposal

"An internal gateway on our existing EKS cluster. One endpoint, a key per team, automatic fallback to a second provider, and a cost dashboard."

Cost and effort

"About 2 vCPU of capacity and a small RDS instance. Three weeks of my time. No changes to application code apart from the base URL."

Success measure

"After 30 days: 100% of LLM spend visible per team, fewer than 1% failed requests, and one provider outage absorbed with no user impact."

Benchmark it yourself

This script also serves as Python practice: async code, streaming responses and percentiles. For rigorous numbers later, use vLLM's own benchmark tool or GuideLLM.

Pythonbench.py
import asyncio, json, statistics, time
import httpx

URL = "http://localhost:8000/v1/chat/completions"   # kubectl port-forward svc/vllm-qwen 8000
MODEL = "Qwen/Qwen2.5-7B-Instruct-AWQ"
PROMPT = "Explain Kubernetes taints and tolerations in 150 words."


async def one_request(client):
    body = {"model": MODEL, "messages": [{"role": "user", "content": PROMPT}],
            "max_tokens": 256, "stream": True}
    start, ttft, tokens = time.perf_counter(), None, 0
    async with client.stream("POST", URL, json=body) as resp:
        async for line in resp.aiter_lines():
            if not line.startswith("data: ") or line.endswith("[DONE]"):
                continue
            chunk = json.loads(line[6:])
            if chunk["choices"] and chunk["choices"][0]["delta"].get("content"):
                ttft = ttft or time.perf_counter() - start
                tokens += 1                     # approx: one streamed chunk = one token
    return ttft, tokens


async def run(concurrency, total=64):
    sem = asyncio.Semaphore(concurrency)
    async with httpx.AsyncClient(timeout=180) as client:
        async def guarded():
            async with sem:
                return await one_request(client)
        t0 = time.perf_counter()
        results = await asyncio.gather(*[guarded() for _ in range(total)])
        wall = time.perf_counter() - t0
    ttfts = sorted(r[0] for r in results if r[0])
    tok_s = sum(r[1] for r in results) / wall
    p95 = ttfts[int(0.95 * (len(ttfts) - 1))]
    print(f"c={concurrency:>3}  {tok_s:7.1f} tok/s  TTFT p50={statistics.median(ttfts):.2f}s  p95={p95:.2f}s")


for c in (1, 8, 32):
    asyncio.run(run(c))

The insight to publish

Self-hosting is only cheap when the GPU stays busy. At low traffic, a small hosted API model often costs less. Showing where the break-even point is, with your own measurements, is the kind of judgment senior engineers are hired for.

Pitfalls to avoid
  • Tutorial hell. Watching without building. Follow the rule of one hour learning for every hour building.
  • Chasing every new tool. The stack in section 03 is enough. Read about new tools, but don't switch plans for them.
  • Skipping the write-up. An unpublished project is invisible to anyone hiring.
  • Forgetting a GPU running. A forgotten g5 node costs about $24 a day. See the next section.
